# AgentQuant 期货交易业务机制

更新时间：2026-05-30

本文档说明 AgentQuant 当前已经代码落地的期货交易业务机制。重点不是分析师如何判断行情，而是系统如何把盘前策略、盘中下单、日终结算、换约、保证金、手续费、滑点和账务复刻成接近真实期货交易的运行链路。

## 一、业务运行机制原则

1. **回测、模拟盘、现实交易同一条业务链路**：系统以 Phase1 盘前策略、Phase2 盘中执行、Phase3 日终结算、Phase4 复盘验收为主线。回测不是单独写一套简化撮合逻辑，而是尽量复用模拟盘/实盘可迁移的推荐、执行、结算、日志和学习机制。
2. **只用当时可见的信息做当时决策**：盘前策略只用盘前可见数据；盘中交易只用当时已发生的分钟线、开盘区间、成交量和执行基准；日终结算价、影子结果和学习结论只在收盘后进入 Phase3/Phase4，不反向污染当日交易。
3. **交易员只执行，不创造策略**：Trader 把 Phase1 的目标仓位翻译成可执行订单，并根据盘中触发条件、保证金、手数、换约和风控边界执行或跳过，不自行生成新的方向判断。
4. **会计师只按事实结算**：Accountant 使用成交流水、合约乘数、保证金率、手续费和官方结算价进行逐日盯市，账务结果不由 LLM、学习记忆或事后解释改写。
5. **多空双向、逐日盯市、保证金占用是核心账户逻辑**：持仓以 signed lots 表示，多头为正、空头为负；账户权益、可用现金、占用保证金、手续费、持仓盈亏和已实现盈亏分开记录。
6. **现实可执行优先于理想化信号**：有交易信号不等于一定成交。系统会检查盘中触发、最小成交量、追价限制、滑点、手续费、保证金容量、合约是否混用、是否需要先换约或先平后开。
7. **业务机制必须可审计**：每笔推荐、盘中触发、成交流水、结算记录、品种日 PnL、完整交易日志和 Phase4 验收结果都要能回查，便于确认是否记错账、算错账或发生未来函数。

## 二、已经代码落地的实际业务运行机制

### 1. 四阶段业务流

- **Phase1 盘前策略**：分析师和 PM 生成每个品种的目标方向、目标仓位、推荐动作、目标手数、合约、参考价格、失效边界和审计快照。
- **Phase2 盘中执行**：Trader 读取待执行推荐，按当前持仓和目标手数翻译为 `open_long`、`open_short`、`close_long`、`close_short` 或 `hold`。
- **Phase3 日终结算**：Accountant 回放当日成交流水，使用同日官方结算价逐日盯市，更新官方组合、日结算、品种日 PnL 和交易流水结算价。
- **Phase4 复盘验收**：Reviewer 检查 Phase1-3 完整性、账务一致性、交易流水入账、分析师信号落库完整性和完整交易日志；Researcher 在此后写入未来可用记忆。

### 2. 多空与订单语义

- 系统支持多头开仓、空头开仓、多头平仓、空头平仓和持有。
- 持仓以 `shares` 表示期货手数：正数是多头，负数是空头，零为空仓。
- Phase1 的“目标手数”会被翻译成 Phase2 的真实订单差额；同向加仓、减仓、清仓和反手都按当前手数与目标手数计算。
- 反手交易采用两步处理：先平掉原方向持仓，再开新方向，避免一笔订单同时混合平仓和反向开仓导致账务含混。

### 3. 合约、主力与换约

- 每个品种使用具体合约代码记账，不只记录品种代码。
- 若当前持仓合约与当日主力合约不一致，系统会生成次日生效的 rollover 推荐。
- 换约推荐记录 `from_contract`、`to_contract`、平仓手数、开仓手数和换约原因。
- 普通策略单如果试图在未换约前把既有持仓混入新合约，执行引擎会要求先换约，避免同一品种下混合多个合约。
- Phase1 会在盘前规划组合里虚拟应用待换约状态，让策略评估尽量面向即将持有的主力合约。
- 换约执行按“平旧合约、开新合约”两条真实腿记录，交易审计里保留换约腿、旧合约、新合约、平仓手数、开仓手数、滑点和手续费，便于计算真实移仓成本。
- 临近最后交易日、交割月或合约详情显示即将到期时，系统会阻止普通策略新开仓；平仓、减仓和换约不受该保护阻断。

### 4. 执行价格、盘中触发与滑点

- Phase2 支持盘中执行确认：15 分钟级别判断信号，1 分钟级别选择成交候选价。
- 开仓通常需要完整开盘区间、VWAP、突破/跌破条件和追价过滤；平仓、减仓和换约属于即时执行优先事项。
- 若没有启用或无法满足盘中确认，系统会使用早盘执行基准价或跳过交易，并写入原因。
- 滑点模型为 tick 模型：买入类动作按基准价加滑点，卖出类动作按基准价减滑点。
- 滑点 tick 数支持按品种配置，例如部分品种 1 tick，部分品种 2 tick；滑点金额由合约最小变动价位计算。
- 成交流水会记录基准价来源、基准日期、实际执行价、滑点模型、滑点 tick 和滑点金额。
- 执行层读取 PandaAI 日行情中的当日涨跌停价，只使用开盘前已知的限价字段，不用当日高低收反推成交。
- 买入类动作若执行价触及涨停、卖出类动作若执行价触及跌停，系统会按“停板无法成交/排队无法保证成交”跳过订单，并写入 `limit_locked_no_fill`。

### 5. 手续费

- 手续费按品种显式配置，要求每个交易品种都有明确规则。
- 支持按成交额比例收费和按每手固定金额收费。
- 开仓、平仓、平今可配置不同费率。
- 手续费按成交价、手数和合约乘数计算，并按配置精度四舍五入。
- 手续费在 Phase2 临时账户和 Phase3 官方日结中都会扣除，最终以 Phase3 结算为准。

### 6. 保证金收取、释放与账户拆分

- 合约静态信息保存合约乘数、最小变动价位、多头保证金率、空头保证金率和交易所信息。
- 保证金率优先从 PandaAI 合约详情读取最低保证金率；若接口无数据或不可用，回退到本地静态合约缓存，并在交易审计里写明来源。
- 开多使用多头保证金率，开空使用空头保证金率；若 PandaAI 只返回单一最低保证金率，则多空共用该动态率。
- 开仓时按 `执行价 * 手数 * 合约乘数 * 保证金率` 占用保证金。
- 平仓时按平掉手数占原持仓比例释放保证金。
- 账户拆分为现金余额、占用保证金、账户权益、可用资金和保证金比例。
- 组合层面存在 20% 总保证金硬门槛；普通机会、强机会和恢复试探都不能突破该硬边界。

### 7. 日终逐日盯市与账务

- Phase3 使用官方同日结算价，不用 LLM 或收盘后解释生成账务。
- 隔夜仓按昨日结算参考价到今日结算价计算持仓盈亏。
- 当日新仓按成交价到今日结算价计算新仓盈亏。
- 当日平仓按成交价与当日参考价计算平仓盈亏，并另保留从原始成本口径得到的已实现盈亏。
- 每日结算后，系统更新组合现金、保证金、账户权益、风险状态、持仓结算价和品种日 PnL。
- 结算引擎会校验权益变动、现金变动和保证金拆分是否一致；不一致会直接报错。

### 8. 品种日 PnL 与交易流水

- `futures_transactions` 保存每笔成交流水，包含品种、合约、动作、手数、执行价、结算价、合约乘数、保证金率、手续费、滑点和审计信息。
- `daily_settlement` 保存组合每日结算记录，包括前后现金、账户权益、保证金、日 PnL、手续费和风险状态。
- `ticker_daily_pnl` 保存品种级每日 PnL，并拆分 holding/new/close/commission。
- 每笔 Phase2 交易在 Phase3 后会回填同日结算价并标记已入账，避免重复结算。
- 未成交推荐不写交易流水，但会在推荐快照中记录跳过原因、市场规则审计、限价/交割保护状态和 warning，避免“没有交易”变成不可解释的黑箱。
- Phase3 会复核当日成交流水是否违反涨跌停限制；若发现理论上不可能成交的流水，会中断结算并报错，防止错误流水进入账务。

### 9. 回测与模拟盘运行方式

- 回测由 `run/backtest.py` 逐交易日调用 `proposal.py`、`order.py`、`settlement.py`、`validate_phase_flow.py`。
- 单日策略生成运行 Phase1；单日交易执行运行 `order.py`；日终结算运行 `settlement.py`；复盘验收运行 `validate_phase_flow.py`。
- 模拟盘/模拟交易可让 Trader 以循环模式等待盘中触发，按配置间隔检查，直到触发成交或到收盘前后完成最终处理。
- 回测和模拟盘共享交易、结算、手续费、滑点、换约、完整日志和学习写回机制。

### 10. 风险、强平与保护

- 当前系统用保证金比例和账户权益回撤做主要账户级风险控制。
- 风险状态分 NORMAL、WARNING、LIQUIDATION，保证金比例过高会进入更高风险状态。
- 回撤保护支持 warning、hard protection、cooling、recovery probe。
- 平仓、减仓、换约和强制风控不应被普通冷却期或持仓保护机械阻断。

### 11. 与真实期货市场的符合度

整体看，当前业务机制已经明显接近真实期货交易：它不是只按收盘价买卖，而是有具体合约、主力换约、多空双向、手数、合约乘数、保证金占用与释放、手续费、滑点、盘中触发、逐日盯市、官方结算价、账户权益校验和完整交易日志。这些是期货策略能否从回测迁移到模拟盘/实盘的关键基础。

但它仍不是完全真实的交易所/期货公司撮合环境。当前更像“可审计的实战近似模拟”，不是逐笔盘口级仿真。尤其是流动性、排队成交、涨跌停、强平细则、交易所夜盘小节、不同合约真实手续费/保证金动态变化、移仓冲击成本等，还可以继续增强。

### 12. 可进一步优化的业务机制

1. **盘口流动性与成交容量**：当前仍未模拟盘口深度、排队、部分成交、撤单、成交量占比上限和冲击成本。
2. **夜盘小节与交易日归属细化**：系统已有夜盘交易日映射校验，但可进一步细化各交易所夜盘品种、休市段、节假日前夜盘取消等现实规则。
3. **真实平今/平昨口径**：系统能识别当日平仓并使用 close_today 费率，但后续可更细拆上海系平今、平昨、先开先平、交易所规则差异。
4. **强平与追加保证金机制**：当前有风险状态和保护逻辑，可继续模拟期货公司追加保证金通知、保证金不足后的强平顺序和强平价格。
5. **成交时段与指令类型**：当前偏市价/基准价成交模拟。后续可支持限价单、撤单、未成交延续、部分成交、开盘集合竞价和收盘前强制处理。

## 三、回测验收项

1. **涨跌停成交保护**：当 PandaAI 日行情提供 `limit_up`、`limit_down` 时，触及涨停的买入类订单、触及跌停的卖出类订单应跳过成交，推荐状态为 skipped，原因写为 `limit_locked_no_fill`，且不生成交易流水；Phase3 也应拦截违反涨跌停限制的异常流水。
2. **动态保证金与回退**：交易审计中应出现 `dynamic_margin`，能区分 `pandaai_future_detail` 与 `static_contract_cache`；接口无数据时回退静态保证金，不中断回测。
3. **换约成本审计**：rollover 交易应能看到 close old/open new 两条腿，以及旧合约、新合约、平开手数、滑点、手续费和换约执行类型。
4. **临近交割新仓保护**：临近最后交易日、交割月或合约月份推断命中时，普通新开仓应跳过并写 `near_expiry_new_entry_block`；平仓、减仓和换约应继续允许。
5. **未成交状态完整性**：无成交交易日或单笔未成交推荐必须保留可解释 no-trade reason，不应再出现无法分类的 unknown。
6. **数据调用频率**：限价、合约详情、保证金率应复用 PandaAI 已有行情/extra 缓存和执行引擎日内缓存，不应导致同一合约同一交易日重复高频 API 调用。
7. **Phase1 信号账本完整性**：每个交易日的推荐快照和 signal 表应覆盖全部 `ticker × analyst` 组合，且同一品种同一分析师只保留最终一条信号，避免业务复盘、交易日志和学习统计口径不一致。
8. **技术参数校准不越权**：Researcher 写入的技术参数情境校准只能影响 Technical Analyst 的指标参数微调，不能跳过 PM、Auditor、Trader、Accountant，也不能改变保证金、手续费、滑点、涨跌停、换约、结算或 20% 保证金硬门槛。
9. **亏损模板观察不改变业务事实**：`loss_template_observation` 只能把已结算亏损模板写成下一轮分析先验；不得改写交易流水、结算、手续费、保证金、换约、涨跌停保护或真实持仓，也不得直接授权或禁止交易。
