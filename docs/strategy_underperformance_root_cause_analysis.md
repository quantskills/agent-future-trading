## 一、最终判断

本次 3 个月回测收益率为负，不是单一的手续费问题、保证金问题、结算错误或程序阶段流失败，而是一个更深的策略问题：系统能够稳定完成“生成信号、下单、结算、复盘学习”的工程流程，但当前信号融合和交易筛选没有形成正期望。亏损来自若干弱品种方向和弱信号模板反复贡献负 PnL，且单笔尾部亏损明显大于正样本盈利；同时资金利用率长期远低于目标，使少数有效模板即使抓对，也无法用足够仓位抵消弱模板的亏损。

最关键的结论如下：

1. 全部 57 个交易日的 Phase1/Phase2/Phase3/Phase4 均为 `completed`，summary 日志没有错误；负收益不是运行失败造成的。
2. 账户最终权益为 4,946,988.56，绝对收益为 -53,011.44，等于累计结算 PnL -50,430.00 再扣除手续费 2,581.44。
3. 完整交易对 102 笔，胜率 43.14%，交易对净 PnL -56,219.69；策略口径交易对 99 笔，净 PnL -63,592.80。核心问题是负期望，而不是交易频率太低或保证金太高。
4. 亏损高度集中：P 多头、ZN 空头、MA 多头、RB 空头、PB 多头、M 多头、C 多头和 BU 多头是主要拖累；I 多头、EB 空头、J 空头、SR 空头虽然有效，但盈利规模不够。
5. 所有 57 天的资本部署状态均为 `under_deployed`，平均保证金比例仅约 2.1%，远低于配置目标 16%-20%。这降低了盈利模板的组合贡献，但不能把负收益解释成“仓位太小”这么简单；真正的问题是低质量信号无法被放大，高质量信号也没有被充分、稳定地识别和配置。
6. reviewer 学习层已经能在事后识别弱模板和强模板，但它是滞后的：必须先发生若干笔亏损，才会形成 `strategy_memory`、`signal_template_performance` 和 `adaptive_policy_state`。在 57 天窗口内，很多亏损已经在学习成熟前发生。

## 二、系统代码层面的理解

AgentQuant 当前是一个四阶段、多智能体的中国期货日频策略系统。

| 阶段 | 入口 | 主要职责 | 关键代码 |
|---|---|---|---|
| Phase1 | `src/run/proposal.py` | 按交易日、按品种生成盘前建议 | `src/graph/workflow.py`、`src/agents/analysis_team/*`、`src/agents/decision_team/portfolio_manager.py` |
| Phase2 | `src/run/order.py` | trader 将建议转为可执行交易，做盘中触发确认 | `src/agents/execution_team/trader.py`、`src/tools/agent_tools/futures_execution.py`、`intraday_execution.py` |
| Phase3 | `src/run/settlement.py` | accountant 逐日盯市、手续费、保证金、官方组合持久化 | `src/agents/execution_team/accountant.py`、`futures_settlement.py` |
| Phase4 | `src/run/validate_phase_flow.py` | reviewer 校验前 3 阶段、写交易日报和学习表 | `src/agents/research_team/reviewer.py`、`reviewer_tools.py` |

源码显示，Phase1 的真实决策路径不是单一 LLM 直接下单，而是：

1. 三类分析师输出结构化 `AnalystSignal`：`technical`、`fundamental`、`commodity_news`。
2. `portfolio_manager` 融合信号、动态权重、品种风险、市场确认和历史反馈，得到目标持仓比例。
3. `TradeAuditor` 做确定性审核，基于市场确认、信号质量、冷启动、历史品种方向表现、strategy memory 和 adaptive policy 决定 `allow/reduce/block/hold`。
4. `capital_utilization_control` 尝试把确认度合格的候选信号放大到目标保证金区间。
5. `holding_rebalance_control` 再做持仓周期、反手、减仓和生命周期控制。
6. Phase2 用 15 分钟确认和 1 分钟成交基准决定是否实际执行。
7. Phase3 按成交回放和结算价计算 PnL，Phase4 写入学习表。

这套工程结构是完整的；问题出在策略质量和反馈时效，而不是系统没有闭环。

## 五、深层根因

### 根因一：信号模板本身没有形成正期望，弱模板反复交易

`signal_template_performance` 和 attribution 报告都显示，亏损不是随机分散，而是集中在一批可命名模板上。

最差模板包括：

| 模板 | 样本 | 胜率 | 净 PnL | 解释 |
|---|---:|---:|---:|---|
| BU long `long_technical_price_trigger_trend_bullish_bearish_neutral` | 2 | 50.00% | -26,213.96 | 胜率不低，但一次大亏过大 |
| P long `long_range_filter_trend_neutral_neutral_bullish` | 2 | 0.00% | -13,522.70 | commodity_news 看多但核心分析师不支持 |
| RB short `short_technical_price_trigger_trend_neutral_bearish_neutral` | 5 | 0.00% | -8,990.41 | 单一基本面/技术空头判断失效 |
| PB long `long_range_filter_choppy_neutral_bullish_bullish` | 5 | 0.00% | -7,721.72 | 区间震荡里基本面和新闻共振看多失败 |
| M long `long_range_filter_choppy_neutral_bullish_bullish` | 6 | 0.00% | -6,318.99 | 同上，区间里做多无效 |
| C long `long_breakout_continuation_trend_bullish_neutral_bullish` | 4 | 25.00% | -2,342.01 | 技术/新闻看多但基本面中性，延续性不足 |

问题不在于“所有信号都坏”，而在于系统没有足够早、足够坚决地区分强模板和弱模板。弱模板在冷启动和样本未成熟阶段已经造成主要亏损。

### 根因二：三类分析师的信号融合存在 horizon 和角色错配

代码层面已经给三类分析师设置了不同自然周期：

| 分析师 | 自然周期 |
|---|---|
| technical | short |
| fundamental | medium |
| commodity_news | event_short |

但数据库中 `signal_context_history` 显示，855 条策略信号画像里有 848 条被归为 `short`。也就是说，最终交易画像高度短周期化，而中期基本面和事件短窗信号被压到同一个短线执行框架中。

这会产生三类问题：

1. 基本面信号本应作为中期锚，但在短线持仓与盘中触发里容易被过早验证或过早否定。
2. 新闻信号是 event_short，适合事件冲击窗口；但在很多亏损样本里，commodity_news 的 Bullish/Bearish 成为方向推动，却缺少足够的技术和基本面共同确认。
3. technical 信号多数为 Neutral，无法提供清晰趋势过滤，导致“新闻/基本面偏多 + 技术中性”的组合在震荡市中反复开仓。

分析师总体信号也能说明这个结构：

| 分析师 | Bullish | Bearish | Neutral |
|---|---:|---:|---:|
| commodity_news | 213 | 147 | 495 |
| fundamental | 84 | 252 | 519 |
| technical | 75 | 69 | 711 |

technical 大部分中性，fundamental 多数中性或偏空，commodity_news 更容易给出方向。当组合进入 `Neutral|Neutral|Bullish`、`Neutral|Bullish|Bullish` 这类弱确认模式时，实际表现很差：

| Signal Combo | 交易对 | 胜率 | 净 PnL |
|---|---:|---:|---:|
| Neutral|Neutral|Bullish | 16 | 37.50% | -26,494.95 |
| Neutral|Bullish|Bullish | 13 | 7.69% | -14,751.96 |
| Neutral|Bearish|Neutral | 10 | 20.00% | -8,986.62 |
| Neutral|Bearish|Bearish | 20 | 50.00% | -4,918.41 |

这说明多智能体融合的核心矛盾不是“分析师太少”，而是不同周期信号被合成为同一类日频目标仓位后，缺少足够严格的模板适配和失效条件。

### 根因三：尾部亏损控制不足，亏损单的规模和持有损失压倒胜率

BU 多头是最能说明问题的样本。BU long 胜率 62.50%，但净 PnL 仍为 -7,921.29，原因是一笔 16 手亏损单造成 -26,457.66。也就是说，系统在方向判断上并非完全失败，但止损、减仓、失效位和持仓生命周期没有把亏损截断。

源码中存在持仓控制：

1. `holding_rebalance_control`
2. `position_lifecycle`
3. `drawdown_control`
4. `ticker_loss_control`
5. cooling period：开仓两天内通常阻止自愿减仓，除非亏损超过保证金的 5%

这些控制偏向避免过度交易和过早反手，但副作用是：当信号本身错误或行情快速反向时，系统可能在短窗口里保留亏损敞口，等到确认失败时亏损已经扩大。

从交易对看，最大亏损单和最大盈利单不对称：

| 项目 | 数值 |
|---|---:|
| 最差单笔 | -26,457.66 |
| 第二差单笔 | -19,611.60 |
| 最好单笔 | +10,796.01 |
| 第二好单笔 | +10,452.37 |

策略负收益的核心不是“亏损笔数略多”这么简单，而是亏损尾部明显更厚。

### 根因四：TradeAuditor 和市场确认层主要是刹车，不是 alpha 选择器

数据库和 attribution 显示，控制层大量触发：

| 控制原因 | 次数 |
|---|---:|
| `market_confirmation_conflict` | 507 |
| `insufficient_quality_support` | 405 |
| `trade_auditor_block` | 403 |
| `cold_start_small_cap` | 336 |
| `market_confirmation_quality_gate` | 267 |
| `news_only_directional_trade` | 174 |
| `analyst_quality_low_tradeability` | 146 |
| `weak_ticker_side_history` | 113 |
| `strategy_memory_weak_block` | 93 |
| `low_quality_news_driven_trade` | 80 |

这说明 auditor 确实在努力阻止低质量交易。但实际完成的策略交易对仍然为负，说明控制层做的是“降低坏信号的仓位和频率”，而不是“主动选择高期望模板并集中配置”。当上游信号池整体边际不足时，auditor 再强也只能减少损失，不能自动创造正收益。

另一个证据是资金部署状态：57 天全部低于目标保证金区间，其中 45 天的低部署原因是 `trade_auditor_block`，11 天是 `llm_neutral`。这意味着系统大量时间处于“有风险控制，但没有足够高质量候选信号”的状态。

### 根因五：资本利用率长期过低，强模板收益被稀释

配置目标写得很明确：保证金占账户权益目标为 16%-20%，常规确认后为 18%。但实际结果为：

| 指标 | 数值 |
|---|---:|
| 平均保证金比例 | 约 2.1% |
| 中位保证金比例 | 约 1.8% |
| 最高保证金比例 | 约 6.3%-6.7% |
| 低于 16% 的交易日 | 57 / 57 |
| 平均距离 16% 下限的保证金缺口 | 约 690,315 |

这不是简单的“应该加仓”。如果盲目加仓，弱模板亏损会被同步放大。但低利用率揭示了另一个问题：系统没有把有限的风险预算有效迁移到已验证强模板。

例如：

1. I long 净 PnL +26,727.77，是最强方向之一。
2. EB short 净 PnL +5,431.55。
3. BU 的某个趋势延续多头模板净 PnL +23,250.81。

这些正样本未能形成足够大的组合权重。系统宁愿长期 under-deployed，也没有在强模板成熟后建立清晰的“逐级加仓”路径。结果是：弱模板造成亏损，强模板贡献太薄。

### 根因六：学习层有效但滞后，冷启动亏损已经发生

reviewer 在 2025-03-31 已经识别出：

| 类型 | 数量 |
|---|---:|
| `strategy_memory` | 40 |
| `protected` memory | 6 |
| `recovering` memory | 10 |
| `watchlist` memory | 8 |
| `weak_block` memory | 16 |
| `adaptive_policy_state` | 13 |
| `signal_template_performance` | 23 |
| `analyst_learning_digest` | 1084 |

它已经知道这些强弱方向：

| 保护方向 | 证据 |
|---|---|
| I long | 9 笔，胜率 66.67%，净 PnL +26,727.77 |
| BU long 某趋势模板 | 4 笔，胜率 100%，净 PnL +23,250.81 |
| J short | 5 笔，胜率 60%，净 PnL +1,764.44 |
| SR short | 9 笔，胜率 66.67%，净 PnL +1,852.00 |

也已经标记这些弱方向：

| 弱方向 | 证据 |

| ZN short | 5 笔，胜率 0%，净 PnL -21,053.00 |

问题在于这些认知大多是“亏损发生后”的学习结果。`anti_overfit.min_samples_for_template` 和 `min_samples_for_policy` 的存在是必要的，避免过拟合；但它也意味着第一阶段必须支付探索成本。当前探索成本过高，主要因为冷启动仓位、弱模板准入和尾部亏损控制没有形成足够严格的组合。

### 根因七：基本面数据新鲜度不足削弱了中期锚

这正好对应了许多亏损组合：核心基本面并没有提供强锚，新闻/技术方向却推动了开仓。

### 根因八：交易成本不是主因，但足以吞噬边际信号

手续费总额 2,581.44，仅占初始资金约 0.05%，不是负收益主因。但在平均每笔交易对净亏约 -551 的情况下，手续费和滑点会显著恶化边际策略。

成交明细显示：

| 项目 | 数值 |

| 完整交易对 | 102 笔 |
| 手续费 | 2,581.44 |
| 估算滑点冲击 | 约 14,610 |
| 最常用成交基准 | `intraday_first_valid_1m_open` 102 笔、`intraday_next_1m_open` 52 笔 |

盘中确认机制跳过了 35 条未触发交易，说明它有过滤作用；但已经成交的交易仍缺乏足够 alpha，成本自然会把微弱优势推成负值。

### 根因九：最终不是结算错误或风险强平问题

需要明确排除几个误判：

1. 不是保证金风险导致亏损：峰值保证金比例只有 6.68%，预警天数 0，强平事件 0。
2. 不是阶段流失败：57 天四阶段全部 completed。
3. 不是交易没有执行：有 154 笔成交流水、102 个完整交易对。
4. 不是单纯手续费过高：手续费只解释 -2,581.44，不能解释 -50,430.00 的交易亏损。
5. 不是没有 reviewer 学习：学习表大量存在，问题是学习滞后和应用不够前置。

## 七、改进方向

### 1. 把交易准入从“方向 + 置信度”升级为“模板 + 位置 + 阶段 + 失效位”

必须让 portfolio manager 和 auditor 更重视以下字段：

1. `signal_template`
2. `price_stage`
3. `price_percentile`
4. `trigger_type`
5. `entry_type`
6. `invalidation_level`
7. `expected_horizon_days`
8. `market_regime`

弱模板不能只靠交易后 attribution 慢慢识别。对于已经暴露出明显问题的模板，应在冷启动阶段就使用更严格的准入条件：

| 模板状态 | 建议 |
|---|---|
| 未成熟模板 | 小仓试探，必须有多源确认 |
| 新闻单边驱动模板 | 必须有 technical 或 fundamental 至少一方配合 |
| choppy/range 内的顺势追涨模板 | 降权或只允许更小仓位 |
| 历史弱模板 | 除非市场确认显著改善，否则 block 或 hard cap |
| 历史强模板 | 允许在确认度合格时逐级加仓 |

### 2. 对尾部亏损建立更硬的失效规则

当前系统有生命周期控制，但仍让少数亏损单变得过大。建议：

1. 开仓时必须写入 `invalidation_level`，没有失效位的方向性新仓只能是极小试探仓。
2. 将止损从“保证金亏损比例”补充为“品种波动/ATR/关键价位失效”。
3. 对 `range_filter` 下的多头追涨或空头追跌设置更短的时间止损。
4. 对单笔亏损超过最近该模板平均盈利的交易，触发模板复核，而不是等样本数自然成熟。
5. 对 BU 这种“胜率高但尾部亏损大”的方向，不应简单 weak_block，而应拆成强趋势模板和弱技术触发模板分别处理。

### 3. 资金部署应服务于强模板，而不是服务于填满仓位

16%-20% 的保证金目标是合理的，但当前实现仍然无法真正部署到目标区间。正确路径不是放宽所有信号，而是：

1. 先定义强模板白名单，例如 I long、BU 强趋势 long、EB short、J/SR short。
2. 对强模板按确认强度逐级释放仓位，例如 0.5x、1.0x、1.5x。
3. 对弱模板即使组合低仓位，也不允许为了补足保证金而交易。
4. `capital_deployment_state.reason_bucket` 不能只记录 `trade_auditor_block`，还要记录“是否存在合格强模板但未被放大”。
5. 将“低部署”分成两类：高质量信号不足导致的合理低部署，以及强模板未放大的错误低部署。

### 4. 让 reviewer 学习更前置，但保持反过拟合约束

reviewer 现在能够事后总结强弱模板，但建议增加“早期风险哨兵”：

1. 单笔异常亏损立即触发临时 cap，不必等完整模板样本成熟。
2. 同一品种方向连续两次亏损，下一次新开仓必须提高市场确认阈值。
3. 同一 signal combo 出现一次极端亏损，应进入 watchlist，而不是等到多笔样本。
4. `adaptive_policy_state` 可以保留 mature policy，同时增加短期 `provisional_policy_state`，带自动过期和回滚。
5. 学习事件必须继续写入 `learning_event_log`，避免把噪声硬编码进 `dev.yaml`。

### 5. 修复 horizon 融合问题

建议 portfolio manager 在融合时显式区分：

| 类型 | 应用方式 |
|---|---|
| technical short | 负责入场时机、突破/回撤确认、止损位 |
| fundamental medium | 负责方向锚和持仓上限 |
| commodity_news event_short | 负责事件窗口增量，不单独决定中期仓位 |

如果最终 `horizon_class=short`，则 fundamental medium 不能被当作短线追涨理由；如果最终是 medium，则 Phase2 的盘中触发不应过度依赖 15 分钟突破。

### 6. 基本面数据质量要进入“可交易性”而不仅是降权

对陈旧严重的品种，建议：

1. 数据陈旧超过阈值时，fundamental 不能输出强方向，只能输出风险提示或低置信度锚。
2. 如果某品种的关键基本面指标长期陈旧，portfolio manager 应要求 technical 和 market confirmation 双确认。
3. 对 CF、SR、PB、M 等陈旧警告高的品种，先降低基本面驱动交易的上限，直到数据新鲜度恢复。

## 八、结论

本次回测收益为负的根本原因是：系统的工程闭环已经成立，但策略闭环仍然是“事后识别弱模板、低仓位防御、少量强模板薄贡献”的状态。它能避免爆仓和流程错误，却还不能稳定把资金集中到正期望模板上。

最深层的矛盾是三件事叠加：

1. 弱模板准入过宽，尤其是 P long、ZN short、RB short、PB/M/C long 等方向。
2. 尾部亏损控制不够硬，导致少数大亏吞掉大量正常盈利。
3. 强模板识别和资金释放太慢，平均保证金比例只有约 2.1%，使 I long、BU 强趋势 long、EB/J/SR short 等有效结构无法充分贡献。

因此，下一轮优化不应简单地“提高仓位”或“扩大 block 名单”。正确方向是：用 reviewer 已经沉淀的模板归因，把交易系统从品种方向层面的粗筛，升级为模板、行情阶段、价格位置、触发形态和失效位的精细化筛选；同时把资金部署只释放给已确认的强模板，并用更硬的失效规则切断尾部亏损。
